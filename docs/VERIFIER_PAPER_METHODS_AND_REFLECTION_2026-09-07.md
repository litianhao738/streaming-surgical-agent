## 当前真正运行的机制与问题

默认 `run_dataset_api_pipeline.py` 仍只执行冻结的 final-only H0。下述修复是在独立研究入口中执行；不能将已接通实验链路解释为默认入口已经升级。


## 母体全文到底怎么做

附件第 5–6 页将两种 memory 分开：每个样本的工作记忆保存预测、候选和问题；数据集先验记忆保存器械、动作、组织和阶段共现统计。后者用于扩充候选和检查合理性，不是自动检索过去视频画面的长期记忆。

论文描述的流程可简化为：

```text
先验库 = 数据集中的器械/动作/组织/阶段共现统计
H = 各任务专家看当前三帧作答
候选 = 用 H 和先验库扩充 IVT 清单
H = 视觉复核候选后的预测
在限定轮数内：
    issues = 检查 IVT-组件矛盾和阶段不相容
    若无 issues：停止
    将 issues 写入本样本工作记忆
    只重新调用涉及问题的专家进行修订
    重新检查约束
生成报告
```

这里的 reflection 有明确问题反馈，但初始问题主要来自结构和先验。一个三元组及三个组件一起看错时，可以通过这些检查。因此不能将“闭环结束”解释成“视觉已被证实正确”。

公开代码与上述方法描述也不完全一致：默认联合预测；候选审核把 `selected` 与 `maybe` 合并；`max_rounds > 0` 只控制一次 `if model_repair`，没有对应多轮循环；修订结果经过规则处理后，四个头中任一非空就可替换四头，没有独立的最终视觉裁判。[候选视觉审核](https://github.com/AlexZhihao/SurgReflect-Hierarchical-Agentic-Verification-for-Multi-Triplet-Surgical-Scene-Understanding/blob/3028fce4a8eb7ba181314b593c0336ad69b9b67b/experts.py#L628)、[修订入口](https://github.com/AlexZhihao/SurgReflect-Hierarchical-Agentic-Verification-for-Multi-Triplet-Surgical-Scene-Understanding/blob/3028fce4a8eb7ba181314b593c0336ad69b9b67b/orchestrator.py#L445)

论文表 3 中完整配置 IVT F1 为 61.12，去掉 Reflection 的 CoT+RAG 为 57.19；但 CoT+Reflection、没有 RAG 的组合为 49.92。以上只是论文所报组合消融，不是“多调用一次 API 固定提升若干点”的证据，也不是本项目复现结果。

另有复现待澄清项：附件没有明确给出先验拟合的视频隔离、平滑和权重数值、请求成本以及逐修改利害统计。公开 `build_from_samples` 直接统计传入样本 GT，示例又对整个 benchmark 建库；照搬到评估数据会泄漏，但不能仅据此认定论文实验实际如何划分。[先验构建源码](https://github.com/AlexZhihao/SurgReflect-Hierarchical-Agentic-Verification-for-Multi-Triplet-Surgical-Scene-Understanding/blob/3028fce4a8eb7ba181314b593c0336ad69b9b67b/rag_store.py#L55)

## 推荐先做：一次反馈式证据审核，限制为撤回可疑修改

**状态：尚未实现或实测，预计 1–2 天可完成一轮小对照。** 冻结 H0、定位、H1、首次中性审核 R0、图片和本体；第二次只检查首次审核是否足以支持已经执行的修改，不产生新候选，不重写整份五头输出，不增加循环。

两条第二审核都输入原图、同一批裁剪和全部原命题，使用同一组具体问题和同一新输出 Schema；反馈臂另外提供首次结论和原始观察文字，明确它们是待核查陈述。问题固定为：证据对应的是同一把器械、同一动作和被作用组织吗；动作是否来自真实时序变化；Target 是否仅在背景可见；删除的依据是否足以覆盖全帧；是否存在反证或看不清。输出同一实例的结构化见证、组织角色（交互目标／仅背景／无法判断）、更新的 PRESENT/ABSENT/UNCLEAR、图像引用和不超过 1000 字符的观察说明。不能为 H0 的帧级标签凭空补造实例关系；引用只能证明输入存在，语义真假仍待实验检验。

```text
R0 = 首次中性审核(图像, H0/H1 分歧)
B0 = 已有局部 Repair(H0, H1, R0)
E0 = 实际标签集合差分(H0, B0)              # 不是仅看 approved 布尔值

控制组 R1c = 原图、全部命题、固定见证问题和 Schema，不提供 R0
反思组 R1f = 相同图片、命题、问题和 Schema，另提供 R0 供核查

对每个组：
    第二审核无效 → 保留 B0，记录失败
    只允许 E0 内且首次、二次都支持的修改
    重新执行现有 IVT/组件依赖检查
    断言最终实际修改是 E0 的子集
    断言失败 → 保留 B0，记录工程失败
```

两个组采用同样的问题、Schema、交集和失败政策，才能区分反馈作用与“多一道门槛所以更保守”。历史 exact-wire repeat 仅作背景，不冒充新样本上的配对盲见证对照。尤其不能只求 `approved` 交集再直接重跑 B：撤回 IVT 新增后，原本被该 IVT 阻挡的组件删除可能变得可执行。必须用首次**实际修改集 E0**限制范围，并检查最终标签差分。不能将首次未执行的删除作为第二次的新修复。固定依赖规则下没有可保留修改时自然返回 H0；接口或断言失败则两臂均复用首次 B0 并记录工程失败。

该版本既可能保住首次有益修改，也可能撤回它们；“修改变少”本身不是成功。它有意只检验能否减少误改，无法补出共同漏检。若第二模型受到首次解释锚定，效果甚至可能劣于盲重审。没有独立证据时不能称为独立裁判。

最小实验建议：8 个新的 Training 目标，按视频和固定时间规则选择，调用前冻结具体帧号、模型、请求与源文件哈希。每目标最多 H0、定位、候选、R0、盲重审、反馈复核共 6 次，合计 **最多 48 次请求**，不自动重试；无候选或无实际修改可跳过后续。此处是调用上限提案，尚无已冻结目标清单或费用报价；执行前须核验模型路由、定价并写入明确预算，不能将旧阶段费用当作新预算。

同时报告 H0、原 H1、B0、盲重审交集、反馈交集；记录各头 micro-F1、集合 Accuracy、有效 GT 数、改对、改坏、部分改善、无收益替换、失败回退和实际费用。另报告 E0 中有害修改被撤回率、有益修改保留率。缺失 GT 按头 mask 排除。全部回到 H0、零修改或只提升合法率均不构成修复成功；小样本开发也不构成泛化证明。方案选择只用 Training，Testing 保持封存。

## 第二条独立路线：借鉴母体的先验候选扩充

这是处理共同漏检更直接的机制，但先做零调用候选覆盖诊断。只用 Training 构建器械—动作—组织共现；评估一个 Training 视频时排除整个该视频。缺失标注不计作负例，阶段只作软提示，不能直接推翻视觉结果。

固定一个小候选预算和排序规则，在完整 100-IVT 本体上保留 H0 候选并扩充替代项；先比较新增候选对遗漏真值的覆盖和候选大小。若没有覆盖收益，就不继续付费。如果有，再用冻结的新 Training 样本验证新增候选能否被视觉审核正确选中。GT 只在候选落盘后算覆盖，不进入单样本推理。

这需要适配候选接口，不能把当前仅支持 H0/H1 差分的审核宣称为已经支持任意新增候选。先验频率也不是视觉真值，不能照搬 `maybe` 当阳性、统计阶段硬覆盖、IVT 强制覆盖所有独立头或全 benchmark 建库。该路线与反馈复核应分别对照，避免无法归因。
