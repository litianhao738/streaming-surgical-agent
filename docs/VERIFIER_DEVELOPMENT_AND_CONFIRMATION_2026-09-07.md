## 实验实际执行了什么

基础采集沿用默认 H0 构造器与配置：三帧因果窗口、一次联合预测 Instrument / Verb / Target / IVT / Phase，OpenRouter `qwen/qwen3.8-max-0902` 严格 Alibaba 路由，temperature=0、reasoning=low、max_tokens=4096。没有修改默认 H0 视觉 prompt、引入 Tracker / Gate / 跨窗口记忆，也没有使用 Batch。

每个目标先生成 H0，再独立盲定位、利用真实裁剪提出 H1。采集阶段未发起旧双假设审核 API，也未读取 GT 标签进行评分。待采集完成后，同一 H0、定位、H1 和图片被两个审核变体共用：

- 数字审核：逐条判断程序生成的帧级存在命题，输出 PRESENT / ABSENT / UNCLEAR。
- 名称审核：只在相同命题上由 Python 确定性展开本体名称；IVT 展开完整 Instrument / Verb / Target 元组。完整本体、系统说明、图片、1000 字符说明 Schema 和生成参数相同，执行先后按目标交替。

两种审核均隐藏 H0/H1 身份及 ADD/REMOVE 方向。A 要求全部修改通过后整份接纳 H1，否则保留 H0；B 从 H0 开始只应用获准且满足依赖的局部修改。删除 IVT 不自动删除组件；添加 IVT 需要其组件已经存在或另获批准；组件不能与保留的 IVT 冲突。Phase 始终保留 H0。A/B 共用一次审核响应，不增加 API 调用。

这是独立研究入口的对照，尚未接替默认纯 API 入口。Schema 合法、引用存在、说明更详细均不能自动证明视觉标签正确。

## 候选上限与共同漏检

在 15 个 IVT 有效目标中，H0 总共漏掉 14 个 GT 标签出现项；H1 只补充其中 2 项，另外 **12 项 H0/H1 都未提出**。这里计的是“目标—标签”出现次数，不是 12 个不同的本体类别。候选同时暴露了 8 个可删除的 H0 错误 IVT，但也新增 9 个错误 IVT、删除了 3 个原本正确的 IVT。

如果事后用 GT 只应用有益的 IVT 修改，并忽略组件依赖，乐观的逐标签 oracle 为 TP=14、FP=8、FN=12，IVT micro-F1 **58.33%**、集合 Accuracy **40.00%（6/15）**。只有 5 个目标存在可利用的逐标签改善；整份 H1 的 IVT 损失优于 H0 的目标有 4 个；允许在 H0/H1 中逐目标选择整份答案时，能使 IVT 集合全对的目标总共 5 个。

该 oracle 是回顾性候选诊断，未给模型、运行时接纳规则或逐帧特判提供 GT。它忽略真实审核和组件限制，不能当可实现的模型分数；它也只约束这批已生成的 H0/H1，不代表所有可能候选的上限。结论同时有两部分：审核仍放行错误并漏接有益修改；候选共同漏检也限制了只审核现有差异的收益。
