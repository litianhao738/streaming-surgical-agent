# 当前 grounded Verifier / Repair 的离线问题分析

2026-09-06。分析对象是刚完成的 Gemini 同步 grounded 实验入口，依据当前代码、12 目标原始输出、4 目标完整任务 GT 及其源实例标注。此次新增 API 调用为 0，没有修改模型、prompt、接纳规则或历史预测。

结论：候选缺少正确新信息，实例定位和覆盖声明不可靠，Verifier 的证据字段没有在本批发挥筛选作用，整帧 IVT 投影还会把一次错误扩散到多个头。接口和 JSON 校验成功不能消除这些语义问题。

## 1. 候选的语义上限很低

四个完整 GT 目标中，三个有效 H1 在 Instrument、Verb、Target、IVT 四头均没有新增任何正确标签。

| 目标 | 候选问题 | Verifier 行为 |
|---|---|---|
| VID103/18501 | 正确 IVT58 换成错误60，丢掉正确 Target2 | 拒绝，保留 H0 |
| VID103/33751 | 新增错误 null IVT94，同时新增错误 Verb9、Target14 | 接纳，造成损害 |
| VID96/14951 | 删除部分错误标签，但新增 IVT36 也错误 | 接纳，只有减少 FP 的部分改善 |
| VID96/25951 | Proposal 的交互证据不足，无有效 H1 | 不进入 Review，保留 H0 |

对已保存的三个有效 H1 和四份 H0，穷举全部八种整帧选择。即使用 GT 帮助选择，最高 IVT micro-F1 也仅为 46.1538%（H0 为42.8571%；TP=3、FP=2、FN=5），IVT 集合全对最多仍为 0/4。最佳组合只是前两目标保留 H0、第三目标用 H1、第四目标保留 H0。

这是使用 GT 的离线候选上限诊断，不是可部署策略、不是新增模型成绩，也不是其他样本的上限。它表明仅修改当前二选一接纳策略，不能补回双方共同遗漏的正确 IVT。

诊断记录：`artifacts/preflight/grounded_gemini_e2e_audit_20260906/candidate_ceiling_diagnostic.json`。

## 2. Locator 的“全部覆盖”声明存在实际错误

VID103/18501 的源实例标注有三个工具：左下 grasper 对应 grasp（IVT7），中部 hook 对应 dissect cystic duct（58），顶部边缘另一个 grasper 对应 retract（17）。Locator 仅返回左下与中部两个框，遗漏顶部工具，却返回 `all_visible_tools_covered=true`；Review 也返回 true。

因此集合中出现正确17，并不证明模型把动作对应到了正确实例。Proposal 将已定位的左下 grasper 解释为 retract，而原 GT 中 retract 对应的是遗漏的顶部实例。帧级集合评分无法暴露所有实例对应错误；不能将上述结果解释成要求给同一个 grasper 无条件补两个动作。

另一个确定的几何问题是 VID96/14951 的首框横跨97.3%图宽，padding后裁剪宽854，等于原图全宽。现有校验只保证坐标不反向、不退化，不能证明裁剪聚焦了接触区域。本轮还有两次反向框被正确拒绝。

依据：`grounded_repair.py` 的框校验、`make_contact_crops`，保存的 `crop_manifest`；源 GT 通过同一数据适配器的 `evaluation.instances` 只读核对。GT 框未进入模型请求。宽框是不是动作错误的直接原因仍未验证，不能据此任意加面积阈值或自动重新解释坐标。

## 3. Verifier 依赖模型自述，缺少逐项修改的可检查对应

六次实际 Review 中，11个实例的44项布尔证据检查全部为 true，六次覆盖声明也全部为 true。没有一次通过这些证据字段触发拒绝；本批接纳差异实际由 `preferred` 决定。

`grounded_repair.py:155` 的 `admit` 校验偏好、覆盖、实例ID、四个布尔项，以及观察文本至少12个字符。它能校验格式和显式否定，不能判断“看见了某动作”是否属实。VID103/33751 中 Proposal 将工具解释成没有本体内交互，Review再次认可，错误null因此通过全部检查。当前提示词已经有 null 不能作为不确定性回退的说明，不能把问题归结为少了一句提醒。

更具体的契约缺口：Review输入包含定位框、裁剪和帧级 H0/H1 集合，但未带入 Proposal 的逐实例 IVT 归属；输出也没有要求每个新增/删除标签对应哪个实例、哪条证据，以及分别支持哪个假设。H0 本身只有帧级集合，没有原生实例归属。当前设计让 Review 自行推断这些对应，无法程序化检查每项修改是否都受到复核。

同一 Gemini 在独立调用中生成和复核，且复用同一组因果图片与定位区域；这不能当成错误独立的第二裁判。它也不表示错误一定相关到何种程度，本批规模无法估计相关性或总体误接纳率。

## 4. Repair 是整帧重建，容易连带改坏

`grounded_repair.py:136` 将候选 IVT 并集投影为 Instrument/Verb/Target；`final_only_grounded.py:114` 整份选择 H0 或 H1。

所以一次错误 IVT94 会同时新增错误 Verb9 和 Target14，确实使 VID103/33751 原本完全正确的 Target 集合变错。这种投影保证标签关系一致，但不能保证每个受影响的头都更准确，也没有逐项保留未被证据支持修改的 H0 标签。

另一方面，任何实例返回 INSUFFICIENT 或空 IVT，就使整帧候选不可用。VID96/25951 的 Proposal 给出了 instrument0，但交互证据不足，最终连原本空的器械头也无法修复。这个保守边界有避免不完整覆盖误删 H0 的理由，不能直接放松为“有个器械ID就接纳”。Phase 明确复制 H0，该目标的 Phase 错误也不在本修复器能力范围内。

## 5. 已知错误类别与待验证解释

四个完整 GT 都有 IVT7（grasper–grasp–gallbladder），H0/H1均未预测7。实际 Proposal 的14个SUPPORTED实例各返回一个IVT，另一个INSUFFICIENT实例为空；Schema本身允许每实例最多三个IVT。但源GT表明至少18501的 grasp/retract属于不同器械实例，不能仅据帧级并集认定模型必须对同实例多选动作。

已确认的是：漏工具、实例归属不正确、grasp/retract相对GT混淆、错误null，以及组织目标相对GT误判均出现在本批。尚未确认的是各错误中视觉证据不足、时序采样不足、类别定义理解偏差各占多少。这里只观察了固定三帧与当前帧裁剪，没有对应证据消融或独立专家判读，不能断言多取帧、换模型或改文字就能解决。

## 最小下一步

优先核查候选的实例覆盖和标签归属，而非继续调整全局接纳偏好。已保存案例足以先整理“哪个实例、增删哪个标签、哪条观察支持”的离线审计，不需要付费重跑。

若之后实施一个小改动，可先将候选与复核契约改为明确记录每项标签增删及对应实例，并检查复核是否覆盖所有修改；保持原H0、模型、图像、一次复核和同一预算。它首先改善可检查性与误改控制，未被证明能够生成缺失的正确 IVT。任何局部接纳还必须处理 H0 无实例归属与 IVT投影约束，不能只按某一头有利就随意拼接。

不要根据这四个目标禁止null、遇到retract就补grasp，或用这里的GT选择线上规则。后续语义试验需另行固定有完整标注的Training样本，继续统计改对、改坏、等损失替换、各头F1/集合Accuracy和新增费用。当前保留冻结H0与全部历史实验。

## 另外发现的工程问题

本次冷进程直接导入 `surgical_agent.research.verification.grounded_repair` 时，复现循环导入：`grounded_repair → api.__init__ → client → schema → grounded_repair.GROUNDED_CONTRACTS`，报 partially initialized module。先导入 API contracts 后再导入则可运行；当前付费 runner 的导入顺序避开了此问题。这影响模块独立复用和复现稳健性，应单独处理，但不能解释已经成功执行的四目标语义错误。本轮未修改该依赖关系。
