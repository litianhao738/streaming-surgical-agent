# I/V/T 与 IVT 分组审核：配对开发实验

用户授权先试两组审核并及时修复工程问题。当前精简默认版本及所有历史结果保持不变。

## 固定协议

八个已检查过的Training目标：VID103 18326/33576、VID23 13176/28876、VID31 40701/73701、VID96 15051/26051。不是新样本确认，也不使用Testing。原始H0、候选池和精简Phase五席回答来自`compact_verifier_paired_20260909_v2_continued`的封存记录。没有根据GT筛选候选或新目标。

control：每个模型一次看全部四头候选，五席并行。

split：I/V/T候选一组、完整IVT关系一组，各有原来的五个模型独立看相同三帧。最多十请求并行，各组不看另一组的评分。缩小候选列表及输出Schema，任务语句指明负责的组；原精简语义定义、图片细节、模型、思考强度、输出上限和标签边界保留。IVT候选本身包含三个组件的含义，不能把这部分语义信息删掉。

两组分别校验后按候选ID合并意见，使用原五份有效评分、均分4新增／均分2删除及组件依赖规则。缺失意见不补成3分或通过；组件组的有效意见不因关系组失败而丢失。再合并同一份Phase结果。没有额外循环、补候选、Tracker、Gate、学习权重或LLM重写。

每目标control 5次、split 10次，总计最多120次新请求，OpenRouter $2、xAI $2、阿里云¥2。复用H0/候选/Phase不计作新调用；没有重试。两组运行顺序按目标交替，目标顺序执行。

预定观察条件：五头等权平均F1提高、IVT F1和平均Precision不下降、总FP+FN减少。所有逐头退化、失败、无收益替换另报，不凭八目标自动替换默认，不在看结果后改阈值。费用按原生账单、估算、未知预留分别报告；时间是审核环节实测，不能当完整Pipeline时间。

首次准备目录`split_review_eight_20260909_v1`只做预检，未执行API；测试夹具对原IVT本体补入组件的预期不正确，修正断言后重新冻结到v2，保留v1。没有修改生产语义或根据分数调整算法。

入口：`scripts/run_split_review_trial.py prepare/execute/score --output ...`。结果在推理封存、原始回答重放后读取GT算分。

## 网络中断与独立恢复

v2计划SHA256：`79e2b9511e990a39ba368f6b3a565063e931d38bfb0166f7004f69c8eab8b146`。原计划120次尝试全部落盘，但后4个目标发生1次Qwen HTTP403和45次跨供应商ProxyError；前4目标60次均解析成功。不能将回退结果和快速失败耗时当成干净的质量／速度结论。原批次仍完整算分留档，原始回答重放及独立15张逐头计数表核对通过。

事后只读网络探测已恢复：代理通路的OpenRouter目录返回200、xAI站点有HTTP响应、阿里云站点返回200。没有修改系统代理或声称已确定断网根因。

新增`recover_split_review_trial.py`：按运输失败状态而非GT／分数选出受影响的VID31 40701/73701、VID96 15051/26051。独立v3恢复目录复用前4目标的全部60份配对回答，仅后4目标重新发起两组审核，最多60次新增请求。原v2失败回答、旧分数和未知计费全部保留；这是公开记录的恢复实验，不是原计划悄悄重试。

再次出现ProxyError即停止后续派发；已经在途的请求等待完成、留档，不自动补发。累计预算包括v2全部费用与未知预留，新增每账户最多1，累计每账户最多3（OpenRouter/xAI美元、阿里云人民币）。网络熔断及累计预算两项离线测试通过。恢复准备曾因账本索引起点检查不匹配而在建目录和付费前停止，按实际0起点修正；没有改动模型输入或答案规则。

恢复统计中的前4目标时间沿用原记录，后4目标使用新记录，因此是跨两次运行的审核等待时间合计；恢复进程本身耗时另报，不能声称它是连续一次完整Pipeline测时。

## 具体机制问题

1. **分支证据不一致与重复门槛。** 一个正确新增IVT在关系组五个评分都是5，但Target组是4/3/3/5/4，均分3.8；器械、动作均分都是5。Target组没有否定票，只有两份不确定，原接纳代码仍要求三个组件均分都≥4，因而阻止该关系加入。该Target已在H0中且最终仍保留，也不能绕过“新增IVT须组件重新过门槛”的规则。这是本轮固定接纳机制与独立审核之间的冲突，不是漏合并JSON或错配候选ID。
2. **独立组件判断没有稳定变准。** 另两个正确Target的评分分别从4.0→2.8、4.2→3.2，失去新增资格。分组后少了完整关系候选的上下文，同时模型存在调用波动；本试验不能将两种影响分离。它们有明确低分否定意见，不能用上一条的“不确定不等于否定”原则一并自动纠正。
3. **候选上限仍在。** 两组候选池完全相同，15个GT IVT出现项只覆盖7个，另外8个没有进入审核。本轮拆分不负责产生新候选，不能解决这些漏检。分组少选了2个错误IVT，却也少选1个正确IVT，Precision微升但F1下降。
4. **可解析不等于语义正确。** 分组有效候选均分从55项增至62项，仍未提高最终指标。分组中另有2份Grok意见把Target专用finding用于其他任务、1份Qwen局部否定不足，继续按原规则作无效意见，不能因格式更完整而放行。

没有按这些帧的GT写例外、放宽阈值或替换默认。后续若测试关系／组件一致性处理，应将“完整关系一致支持、组件仅不确定”与“组件明确反驳”分开，并在新样本确认；本轮尚未实现或验证该新规则。

## 保存与结论

分组审核模块、隔离执行入口、冻结输入、原始回答、失败账本、恢复协议、指标和独立审计均保留。当前默认配置和原接纳算法未修改，未提交／推送GitHub。

本轮实际修复了实验执行器遇到代理错误仍连续派发的问题，并补齐恢复时原费用预留与请求复用核验。三项分组单元测试、两项恢复测试、120份真实请求模板的零API模拟检查及Ruff通过。没有把工程修复声称为视觉准确率提升。**结论：两组审核没有通过开发标准，不替换默认，也不继续扩大该配置。**
