## 2. 必须先补的真实接入缺口

`src/surgical_agent/systems/final_pipeline_factory.py` 仍显式拒绝 final-only H0。
`run_final_dataset_pipeline.py` 和既有 A/B/C/D 配置对应旧 ranked、三 scope 架构。
最近五席实验是独立的 H0 → 候选 → 审核 → 局部修复入口，尚无完整 Tracker/Gate 集成。
新 Gate 训练器当前拟合两个独立诊断模型，也不等于正式四格要求的同一份 Gate 权重。

五天目标采用一个明确版本的 final-only 端到端适配：

```text
三帧因果图片 → 冻结 H0（可从已验收缓存读取）
Tracker T0/T1 → 仅在决策侧提供带状态/可用性标记的预测特征
H0 + 决策特征 → 结构检查 → 固定规则或学习 Gate
  → 保留 H0，或运行同一个有轮数上限的 Verifier/Repair
  → 修改后校验、明确失败/回退状态 → 最终输出 → 独立 GT/mask 评分
```

该适配需新版本协议和入口，不能简单删除旧 factory 的兼容性拒绝。
它是整次交互修复路由，Phase 保持 H0；不冒称已经完成旧三 scope、语义 Memory/Workflow 的全部迁移。
本轮不引入跨窗口语义记忆；Tracker 可保持因果轨迹状态。所有组的状态重置、帧时钟、失败行为相同。

## 3. 唯一主实验：Tracker × Gate 四格

| 组 | Tracker | Gate 决策 | Verifier/Repair |
| --- | --- | --- | --- |
| A_base | 关闭、显式 mask | 同一份固定规则 | 相同冻结版本，按规则触发 |
| B_tracker | corrected 预测 | 同一份固定规则 | 相同冻结版本，按规则触发 |
| C_gate | 关闭、显式 mask | 一份冻结学习 Gate | 相同冻结版本，按 Gate 触发 |
| D_full | corrected 预测 | 与 C 相同的 Gate 权重 | 相同冻结版本，按 Gate 触发 |

纯 H0 是附加参考行，不占四个消融名额。“去掉 Gate”指不用学习 Gate，保留规则路由，不能把 A 写成纯 H0。
主对照为 B−A、D−C（Tracker）、C−A、D−B（学习 Gate），以及 (D−C)−(B−A) 交互。

冻结与实现要求：

- 主 H0 暂用当前 OpenRouter Gemini 研究版本；朋友其他模型的 H0 单列模型比较，五天内不默认展开成每模型四格。若另选 H0，只能按 Training/Validation，且必须重查对应收益标签与 Gate，不能用 Testing 选模型。
- 四格共享逐字相同的 H0 缓存。这明确将本轮 Tracker 作用限定在 H0 后的决策侧；不代表 Tracker 参与初始视觉预测的效果。
- B 必须确实消费 Tracker，例如同一规则在 T1 加入器械集合分歧证据；不能让 Tracker 只进入学习 Gate，使 A/B 先天相同。分歧为软证据，不将独立头投影差当硬错误。
- 在收集标签前固定 final-only 规则风险定义和共同阈值；不伪造 H0 confidence。真正空检测、缺失/失败与关闭需区分。
- C/D 使用一个模型、同一特征定义和阈值；每个训练观察同时提供 T0/T1 视图，两视图合计权重 1，视频整体划分，不能当两份独立样本。
- 固定模型、提示、候选、证据契约、接纳阈值、失败处理和最多三轮；不按 GT 选某帧最好轮。此次检验现有机制，不同时增加 RAG 或反思模块。
- Tracker 不改变图片选择或审核输入；这使同帧被触发时的修复机制相同。整段顺序仍需执行独立的各组路由、预算和状态，不能拿 GT 拼装最终输出。
- 四格给相同的每视频预算上限与分配规则，实际调用不同是结果。报告真实新增费用与假设独立部署的等效成本；复用缓存不能报告为零部署成本。
- Training 使用目标视频排除的 OOF；独立 Validation/Testing 用 Training 上训练的 full Tracker。Gate 的开发视频留出分数不冒称整个上游系统完成嵌套无泄漏交叉验证。

## 5. 规模、费用和评测边界

建议先固定 Training 40→最多160目标、Validation 40目标、最终四格最多200目标作为五天先导规模。
最终目标可在八个 Testing 视频各预先固定一段连续25个标注目标，起点按冻结的时间规则选取；首次 Testing 执行前所有选择与模型冻结，之后不能据结果调参。
若只运行片段，输出和标题必须写“预登记片段子集”，不报告完整 Testing split 成绩；片段需要真实因果历史与明确重置，不能利用未执行的前文状态。
预检发现某视频不足或缺标注时，按预先定义的资格规则记录覆盖，不临时换成容易帧。
完整 split 是后续扩展目标：H0 缓存、Tracker 推理覆盖、API 实测吞吐全部验收后才能给出可信工期。

同步调用上限按现有五席最多三轮计算：每次修复最多 3×(1 提案+5 审核)=18 POST。
已有合格 H0 时，40 个训练目标最多720个修复 POST；缺 H0 再加40，即既有计划的760。
Training160 + Validation40 的修复上限为3600；最终200目标×4格上限14400；合计18000个修复 POST，另计缺失 H0。
完全相同的请求可复用缓存，但不能预先按必然复用缩减上限，也不能将缓存回放的耗时充当真实 API 延迟。
按历史12目标粗线性外推，18000次修复调用约是原生美元数十至百美元、另有人民币通道费用的量级；这不是当前报价或余额核验。
每阶段执行前必须冻结目标、调用上限及分账户预算，并用首批实测费用/吞吐更新后续预计。用户旧有“15美元余额”不能当今日已核实余额。
本计划未启动付费阶段。

最终报告必须包括：

- I/V/T/IVT/Phase 各头有效 GT 数、micro-P/R/F1、集合 Accuracy、五头全对率；缺失 GT 按任务 mask 排除。
- 相对同一 H0：改善、改坏、混合、无收益替换、不变、不可评分，以及新增/删除正确与错误标签数。
- Gate 触发率、有益修改放行/漏放、无益/有害修改放行；不能只报告 Gate 分类准确率。
- 每帧/每视频 API 调用、费用、实际延迟、Tracker 耗时、失败和回退；将生成收益标签的离线成本与上线推理成本分开。
- 按视频配对结果和视频聚类不确定性。帧多不等于独立视频多；先导片段不能证明完整长视频性能。
- 候选覆盖与审核通过率仅作机制诊断，不代替最终语义指标。

朋友交付至少需要：每模型精确标识/提供商、split/video/frame、最终五头、原始响应与失败、输入窗口及版本hash、usage/费用。
已有 Testing H0 可以留存，但模型选择和 Gate 调参阶段不查看其 GT 排名。
